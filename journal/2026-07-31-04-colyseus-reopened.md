# 04 — 아침에 버린 Colyseus를 저녁에 다시 데려오다

> 2026-07-31 · 작성: Claude (개발 세션 AI) · 방향 결정: Hakhyun

일지 03에서 "편의보다 원칙이 이긴 첫 사례"라고 썼다. 몇 시간 만에 그 결정을 뒤집었다. 그리고 이 번복이 부끄러운 일이 아니라 **기록할 가치가 있는 일**이라서 이 일지를 쓴다.

## 전제가 바뀌면 결정도 바뀐다

Colyseus를 뺐던 논리는 이랬다: 바이너리 상태 동기화는 "문서만 읽고 봇을 만들 수 있어야 한다"(P6)와 양립하지 않는다.

그런데 오늘 두 가지가 결합됐다. 먼저 **공식 MCP 도구**를 만들었다 — Claude Code 같은 AI 에이전트가 `join / look / goto / gather / say` 다섯 도구로 게임에 입장해 플레이한다. 이 프로젝트를 열고 "나무 캐줘"라고 말하면 끝이다. 그리고 Hakhyun이 물었다: **"봇은 전부 AI가 만든다고 가정하면? JS만 돌아도 되지 않나?"**

맞는 말이었다. 봇 제작자가 와이어 프로토콜을 직접 만질 일이 없다면 — MCP 도구를 쓰거나, LLM에게 문서와 공식 SDK를 주고 짜게 한다면 — 밑바닥이 JSON이냐 바이너리냐는 내부 구현 문제가 된다. P6의 실질은 "같은 와이어"가 아니라 **"공식 접속 계층이 모두에게 평등하게 열려 있다"** 로 옮겨간다. 그 전제 위에서는 Colyseus의 이득(상태 자동 동기화 — 앞으로 시장·큐·창고가 붙을수록 커진다, 존별 룸 수명주기, 재접속 처리)이 순수하게 남는다.

그래서 GDD의 결정 기록에 서문을 달았다: **"결정은 새 근거가 나오면 재개봉한다. 이 표는 현재 유효한 결정이지 불변의 서약이 아니다."** D7이 그 첫 사례다.

## 전환은 반나절이면 됐다 — 분리가 밥값을 했다

일지 03의 수칙 "게임 로직(world.ts)은 네트워크를 모른다"가 여기서 정확히 밥값을 했다. 이동·채집·리스폰 판정 코드는 **한 줄도 바뀌지 않았다.** 갈아낀 것은 네트워크 계층뿐이다: 수제 WS 서버 → Colyseus 룸, 수제 상태 방송 → 스키마 자동 동기화. world가 진실이고 스키마는 그 투영이라는 구조는 유지된다.

스모크 테스트 4건, MCP 테스트 3건, 브라우저 사람 캐릭터 + CLI 봇 동시 접속, 프로덕션 번들 검증까지 전부 통과한 상태로 마쳤다. PROTOCOL.md는 v0.2 "룸 계약 문서"로 다시 썼다 — 여전히 헌법이고, 여전히 테스트가 문서를 검증한다.

## 오늘의 함정 두 개

**ES2022 class field가 동기화를 조용히 죽인다.** Colyseus 스키마는 프로토타입에 접근자(getter/setter)를 심어 변경을 추적하는데, 최신 TS의 class field(defineProperty 시맨틱)가 이를 데이터 프로퍼티로 덮어쓴다. 에러는 없다. 상태만 영원히 비어 있다. 빌드 도구 설정(tsconfig)에 기대는 대신 `declare` 필드 + 생성자 할당으로 바꿔 도구와 무관하게 안전한 형태로 못박았다.

**조인 직후 메시지는 유실될 수 있다.** 서버가 onJoin에서 바로 보낸 메시지는 클라이언트가 핸들러를 등록하기 전에 도착할 수 있다. 그래서 클라이언트가 준비 시점을 정하는 요청-응답 구조로 바꿨다: 핸들러 전부 등록 → `hello` 전송 → `welcome` 수신. 프로토콜 문서에 핸드셰이크로 명문화했다.
